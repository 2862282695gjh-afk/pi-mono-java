ADR-0044：按普通提交限制非文档新增行

Change class仓库 CI 架构变化

Context

变更前的 CI 只执行 Spotless 与 Maven verify，没有约束提交的新增规模。构建成功不能保证提交易于评审、定位和回滚，因此需要在构建前增加仓库级提交粒度门禁。

产品要求每个提交不得新增超过 2000 行代码，文档不计入。这里的“每个提交”需要在目标分支可能前进、主题分支可能合并最新 main 的 Git 历史中保持稳定语义。

Decision drivers

  • 直接约束单个可评审、可回滚提交，而不是限制整个 PR 的功能规模。
  • 文档新增不消耗代码行额度，删除代码也不能抵扣新增代码。
  • 不依赖 GitHub API、语言识别服务或额外权限。
  • 支持目标分支前进以及主题分支合并最新 main 的既有工作流。
  • 门禁算法可在本地用同一脚本和 Git 对象复现。

Considered options

限制 PR 汇总新增行

优点：实现简单，GitHub 页面也能近似展示。
缺点：两个清晰的小提交会因累计规模被拒绝，无法落实“每次提交”的要求；后续删除还可能掩盖早期超大提交。拒绝。

依赖人工评审判断提交规模

优点：无需 CI 变化，可以按场景自由判断。
缺点：执行不一致且发现太晚，无法形成自动门禁。拒绝。

用 Git numstat 逐普通提交统计非文档新增行

优点：准确区分新增与删除，结果可复现，能通过路径规则排除文档，并允许一个 PR 包含多个合规提交。
缺点：CI 需要完整 Git 历史；二进制内容没有文本行数；合并提交没有唯一的父提交差异。接受。

Decision

  • 新增 scripts/check-commit-additions.sh，接收 base/head revision 并以共同祖先确定检查范围。
  • 按历史顺序检查范围内所有非合并提交；合并提交不重复统计，其包含的非合并提交仍受门禁约束。
  • 使用 rename-aware git diff-tree --numstat 统计文本新增行，只累加 additions 列。
  • 每个提交新增非文档行不超过 2000 时通过；2001 行起失败，删除行不能抵扣。
  • 排除文档目录、文档扩展名及标准仓库文档文件；目录外的应用 HTML、配置、测试和脚本仍计入。
  • Checkout 使用完整历史，并在现有 Spotless/Maven 门禁前运行检查脚本及其回归测试。

Intentional difference

架构变化：CI 从只验证最终源码状态，扩展为同时验证 PR 的提交历史结构。产品约束：2000 行是提交评审粒度上限，不是运行时、模块或 PR 总量限制。文档排除属于明确产品规则，不代表文档无需评审。

Consequences

  • 正面：超大代码提交在构建前被确定性拒绝，并给出提交和逐文件证据。
  • 正面：大型功能可以拆成多个各自合规、可理解的提交。
  • 正面：文档、ADR 和生成设计图不会占用代码额度。
  • 代价：GitHub Actions 必须执行完整历史 Checkout，增加网络与存储开销。
  • 边界：二进制文件没有文本新增行；其大小和适用性继续由其他规则及评审约束。
  • 边界：合并提交不单独计算，避免把目标分支已有历史重复计入；合并所包含的普通提交逐一计算。

Validation

  • 用临时 Git 仓库覆盖 2000/2001 边界、文档排除、多提交累计和重命名。
  • 执行 Bash 语法检查、ShellCheck、脚本回归测试和当前分支提交范围检查。
  • 执行现有 Maven verify、Git diff 检查及设计文档/PlantUML/SVG 验证。
