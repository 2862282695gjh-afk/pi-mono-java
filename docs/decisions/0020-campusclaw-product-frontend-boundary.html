Context

改造前的前端把 Service URL、凭据、Runtime Session ID、ETag、原始 SSE Event 和 JSON payload 作为主界面元素。该形态适合接口联调，但用户实际需要选择 Agent、管理会话、发送消息、查看活动和控制执行。

HTTP 1.38.0 同时确认：Path、Query、JSON 和 SSE data 只使用 lowerCamelCase；提交消息的 POST 返回请求范围 SSE，断线不取消已经接受的执行，也没有 Idempotency-Key。响应头到达后若连接中断，客户端不能判断是否安全重放，盲目重试会产生重复 User MessageEntry。

Considered options

继续扩展调试台

Pro：改动最少。
Con：产品信息架构继续围绕内部 operation，内部身份、并发版本和事件模型越过浏览器边界。拒绝。

隐藏高级字段后让产品页面直连 Runtime

Pro：可以快速完成视觉改造。
Con：隐藏 DOM 不能解决浏览器认证、授权、内部资源身份和安全 Event Schema。拒绝作为生产架构。

产品 UI 经公共 bridge，直接 Runtime adapter 仅作过渡

Pro：用户模型稳定，生产责任清晰；当前仓库仍可在内部环境验证界面和 HTTP 1.38.0。
Con：生产集成仍依赖尚未逐项评审的公共 Agent/Chat/Attachment/Event 契约。接受。

Decision

  • 生产浏览器只调用 mate-service 公共 HTTP/SSE；mate-service 终止认证、执行授权，维护公共 Chat 与内部 Session 的映射，并投影浏览器安全 Event。
  • 产品主界面只展示 Agent、会话、消息、附件、模型、深度思考、工具活动和粗粒度执行状态；Runtime sessionId、ETag、凭据、原始 JSON/SSE 和内部错误不进入产品主流程。
  • 过渡 adapter 严格消费 HTTP 1.38 lowerCamelCase，不提供 snake_case 双读或双写兼容。
  • 初始消息的 HTTP 200/SSE 响应头只启动 running 状态，不清空 Composer 草稿。只有 SSE user.message 或 GET Events 中新的、内容一致的 User Entry 能确认持久化并清空未编辑草稿。
  • 若断流后历史仍无法确认本次 User Entry，发布 OUTCOME_UNCERTAIN、保留草稿且不提供盲目重试动作；若 User Entry 已确认但流中断，发布 STREAM_INTERRUPTED 并以持久化历史为权威。
  • Steer、FollowUp、Abort 分别产品化为“调整方向”“加入队列”“停止”；“调整方向”不表示硬中断当前模型调用或工具。
  • 工具 started/completed/result 合并为一个可展开活动卡；持久化 completed/result 覆盖瞬时预览。

Consequences

正面：主界面围绕用户任务，Runtime 可独立演进；HTTP 字段错位能由契约测试发现；请求已受理后的网络故障不会因为前端自动清空草稿或提示普通重试而放大成重复执行。

负面：短暂断流时草稿可能在 Composer 中多保留一段时间；当前确认机制依赖对话已加载的 Entry 集合和完整历史分页；公共 bridge 尚未完成，直接 adapter 仍只适合内部过渡集成。

后续：逐项设计公共 Agent、Chat、Attachment、Model Catalog、队列项和 SSE 契约，并把现有 Vitest 契约用例扩展为真实后端浏览器 E2E 与视觉回归。
