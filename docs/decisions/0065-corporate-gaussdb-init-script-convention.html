Context

源码基线中，模块 session_schema.sql 以说明注释和 BEGIN 开头，先集中倒序删除全部表，再按顺序创建表，并以 COMMIT 结束。同步脚本把该文件字节级复制成公司交付脚本。

公司代码仓要求交付脚本以固定的 claw 数据库、Schema、{dbUser} Owner 和授权语句开头，不使用 BEGIN/COMMIT，并将每个 DROP TABLE IF EXISTS 紧邻放在对应 CREATE TABLE 之前。

start-dev.sh:initialize_database 会直接在已选定的本地数据库和 Schema 中执行模块脚本。如果把公司 {dbUser} 占位头部写入模块脚本，独立开发流程将无法直接执行。

Considered options

只手工修改公司镜像文件

优点：改动小。
缺点：campusclaw/scripts/install 是生成目录，下次同步会覆盖修改，预推送门禁也会拒绝漂移。拒绝。

把公司头部直接写入模块规范脚本

优点：仍可字节级复制。
缺点：本地开发脚本会执行未替换的 {dbUser}，并重复承担已由 start-dev.sh 完成的数据库与 Schema 选择。拒绝。

用公司头部模板与模块表 DDL 生成交付文件

优点：头部和通用表结构各有单一可编辑源，同时保留本地开发与公司交付语义。
缺点：同步脚本需要组合两段 SQL，不再能用整文件 cmp 验证。接受。

Decision

  • scripts/templates/initdb_gaussdbv5-header.sql 保存公司要求的七行头部：\c claw;、建立 claw Schema、设置 search_path、设置 {dbUser} 用户路径、转移数据库与 Schema Owner，以及授予数据库全部权限。
  • 模块 session_schema.sql 保留本地开发说明、集中 DROP 块和事务语义，不包含公司占位头部。
  • 公司交付文件不包含 BEGIN 或 COMMIT；八张 t_ 表的每个 CREATE TABLE 必须由同表 DROP TABLE IF EXISTS 在紧邻前一行引导。
  • stage_database_install_script 先输出公司头部，留一个空行，再由 emit_corporate_table_ddl 过滤说明、原集中 DROP 块和事务语句，为每个建表语句注入对应删表语句。
  • 生成门禁逐字校验头部，拒绝事务包裹，校验 DROP/CREATE 名称、数量和紧邻顺序，并保持镜像与暂存输出一致。
  • 表、列、索引、约束和中文 COMMENT ON 内容不变；不新增 Maven 依赖。

Intentional differences

  • 产品约束：公司文件使用固定的 claw 数据库与 Schema 头部、{dbUser} 占位符和逐表删建样式。
  • 架构变化：公司文件由整体字节级复制改为“头部模板 + 规范表 DDL”组合生成。
  • 执行语义：公司交付脚本移除事务包裹后，初始化失败可能保留已完成的前置语句；部署平台必须显式报告失败并由操作人员处理部分初始化状态。模块本地开发脚本的事务语义不变。

Consequences

  • 正面：公司交付文件的首行和执行顺序可由自动化门禁精确验证。
  • 正面：通用表结构仍只有一份规范源，公司头部和无事务样式不会影响本地开发。
  • 代价：公司脚本不再与模块脚本整文件相同，需要分别校验头部和表 DDL 主体。
  • 代价：无事务初始化不具备全或无原子性，这是明确接受的公司脚本规范。
  • 边界：头部中的 CREATE SCHEMA claw; 和 Owner/授权语句由公司发布平台在目标环境执行；AgentService 不执行该文件。

Validation

  • 执行镜像布局回归，验证公司头部、镜像/暂存一致、表 DDL 主体同源与安装目录唯一性。
  • 执行 Bash 语法和 ShellCheck，并重复执行同步 dry-run 验证无漂移。
  • 校验公司 SQL 无 BEGIN/COMMIT，八个 DROP/CREATE 名称和紧邻顺序一致，并与模块脚本的建表清单一致。
  • 执行 PlantUML/SVG/XML、Markdown 图路径和源链接、以及 git diff --check 验证。
