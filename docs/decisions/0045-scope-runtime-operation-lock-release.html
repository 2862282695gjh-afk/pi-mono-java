Context

源码基线使用 256 个 ReentrantLock 条带串行化同一 Session 的事件接受、控制消息和执行收尾。RuntimeSessionEngineRegistry#lockOperation 只调用 lock()，#unlockOperation 由调用方在各自的 finally 中调用。

现有调用点虽然成对释放，但该 API 将锁生命周期拆到两个公开方法：注册表不能保证未来调用者一定进入 finally，静态分析也无法从加锁方法本身证明异常路径会释放锁。一次漏解锁会永久阻塞映射到同一条带的后续 Session 操作。

Decision drivers

  • 锁释放必须由拥有加锁动作的同一抽象负责。
  • 正常返回与运行时异常必须共享同一个 finally 释放路径。
  • 保持现有条带数、哈希映射和串行化范围，不改变业务契约。
  • 让新增调用点无法获得一个需要手工配对的公开解锁方法。

Considered options

保留两个公开方法并依赖代码评审

优点：不修改调用接口。
缺点：释放仍是调用方约定，新增异常分支或提前返回时可能遗漏，静态分析告警仍然成立。拒绝。

返回 AutoCloseable 并使用 try-with-resources

优点：调用点语法简洁。
缺点：锁仍在创建 guard 的方法内获取、在另一个对象中释放；保证分散在两个抽象中，分析工具也未必能证明配对。拒绝。

由注册表执行作用域操作

优点：lock() 与 unlock() 位于同一方法和显式 try/finally；调用方不能忘记释放；返回值与无返回值操作都可表达。
缺点：调用方需要把临界区表示为 Supplier 或 Runnable。接受。

Decision

  • 删除公开的 lockOperation 与 unlockOperation。
  • 新增 withOperationLock(sessionId, Supplier<T>)，在获取条带锁后执行操作，并在 finally 中释放。
  • 新增 Runnable 重载并委托给同一 Supplier 实现，不复制锁生命周期逻辑。
  • 事件接受、Steer/FollowUp、Abort 与执行收尾全部通过作用域 API 执行。
  • 增加跨线程回归测试：临界区抛出异常后，另一线程必须能在有界时间内完成同一 Session 的下一次操作。

Intentional difference

架构变更：内部调用由手工加锁/解锁协议改为注册表托管的作用域操作。条带映射、并发顺序、异常传播、HTTP、SSE 和持久化行为保持不变。该决策描述 CampusClaw Java 目标实现，不宣称 pi 存在相同 API。

Consequences

  • 正面：任何已提交操作无论正常返回还是抛出运行时异常，锁都会在 finally 中释放。
  • 正面：未来调用者无法直接获取锁后遗漏解锁。
  • 正面：静态分析可以在一个方法内验证锁生命周期。
  • 兼容性：同一 Session 和条带冲突 Session 继续串行执行。
  • 限制：临界区仍不得执行无界阻塞操作；本决策只保证异常路径释放，不改变锁的可中断性或公平性。

Validation

  • 执行 RuntimeSessionEngineRegistryTest，验证异常后另一线程可重新取得同一 Session 的锁。
  • 执行 Session 控制与 Runtime Event 回归测试，确认作用域 API 没有改变业务结果。
  • 执行格式、Checkstyle、模块测试、公司镜像同步与 Git diff 检查。
  • 验证设计文档不含 Mermaid、PlantUML 为 ASCII、SVG 与源码链接有效。
