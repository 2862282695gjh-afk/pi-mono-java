ADR-0044：保留 Runtime 模型解析异常因果链

StatusAccepted
Date2026-09-03
Source baselineorigin/main@c9d858bc8261bf07f5585f545b53495bf2226a56
Observed sourcemodules/coding-agent-cli/src/main/java/com/campusclaw/codingagent/runtimeapi/model/RuntimeModelManager.java 的 resolveAvailableModel；modules/coding-agent-cli/src/main/java/com/campusclaw/codingagent/runtimeapi/error/RuntimeApiException.java 的构造器

Context

源码基线先校验模型是否位于 Agent 的可用列表，再调用具体 Model Manager 解析模型。除 MANAGER_UNAVAILABLE 外，解析阶段抛出的 RuntimeApiException 会被转换为公开的 MODEL_NOT_AVAILABLE，避免客户端区分“未授权使用”和“未配置”等内部状态。

转换分支创建新异常时没有保留已捕获异常。由于 RuntimeApiException 同时禁用了自身栈跟踪，原始错误码和因果关系会完全丢失，进程内诊断也无法恢复。

Decision drivers

  • 继续保持公开接口的防枚举错误语义。
  • 保留异常转换前的内部错误分类和因果关系。
  • 不恢复稳定业务异常自身的栈跟踪开销。
  • 不改变 HTTP 状态、响应字段或国际化消息。

Considered options

继续丢弃原异常

优点：无需修改异常类型。
缺点：错误转换后无法定位原始分类，也会持续触发异常信息丢失检查。拒绝。

在默认接口中记录日志后丢弃 cause

优点：日志中可以留下原始错误。
缺点：接口默认方法需要承担日志策略，进程内调用方仍无法检查因果链，并可能与更外层的失败日志重复。拒绝。

由包装异常保留 cause

优点：使用 Java 标准异常链保留原始错误，调用方可按需记录或检查；HTTP 边界仍只使用外层错误码。
缺点：异常存活期间会同时引用原异常。接受。

Decision

  • 为 RuntimeApiException 增加接受 Throwable cause 的构造器。
  • 新构造器保留 cause，同时继续关闭 suppression 和包装异常自身的 writable stack trace。
  • resolveAvailableModel 将非 MANAGER_UNAVAILABLE 的原异常作为 MODEL_NOT_AVAILABLE 的 cause。
  • MANAGER_UNAVAILABLE 仍原样传播；可用列表直接拒绝仍不创建虚假的 cause。

Intentional difference

内部错误传播架构变化：稳定业务异常可在错误码转换时携带内部 cause。产品约束保持不变：HTTP 错误处理器只序列化外层 MODEL_NOT_AVAILABLE，不向客户端暴露原始错误类型、消息或栈。

Consequences

  • 正面：静态检查和运行时诊断均可确认原始异常没有在 catch 块中丢失。
  • 正面：模型存在性与 Agent 配置状态仍不能通过公开响应枚举。
  • 边界：cause 仅存在于服务进程内，除非上层显式记录，否则不会自动写入日志。
  • 测试：必须同时断言外层错误码为 MODEL_NOT_AVAILABLE 且 cause 与原异常为同一实例。

Validation

  • 运行 RuntimeModelManagerTest 和 RuntimeErrorCodeTest。
  • 运行 coding-agent 模块相关测试、Spotless、Checkstyle 和 Git diff 检查。
  • 同步并验证 campusclaw 公司镜像。
