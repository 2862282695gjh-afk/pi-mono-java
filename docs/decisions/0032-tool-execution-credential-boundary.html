Context

变更前源码从 POST Events 读取 X-HW-ID、X-HW-APPKEY、Authorization，并把这三项值同时发送给 Agent binding、Skill binding、tool metadata 和 tool execute。新的接口契约还要求 POST Events 读取精确命名的 access-token，同时明确哪些请求可以携带这些值。

当前行为定义如下：POST Events 读取四项值；这些值只在本次 Agent 执行及其 Child 调用期间由内存对象持有，不写入数据库、Event、Prompt、模型消息或日志；Agent binding、Skill binding 和 tool metadata 查询不携带这些值；只有 Mate Tool execute 请求携带收到的非空值。发送 execute 前必须具有 access-token、X-HW-ID 以及 AppKey/JWT 至少一种，否则不发送 execute 请求并返回工具执行失败，但 POST Events 本身不因此被拒绝。执行结束后 Runtime 不再主动持有这些值。

Runtime 不是这些凭据的认证权威，不因 Header 组合或 Bearer 形状增加本地认证错误。

Decision drivers

  • 只有真正需要认证授权的 execute operation 携带敏感 Header。
  • 让“发现无凭据”成为 Java 方法签名可证明、测试可回归的边界。
  • 明确 Runtime、Child 与 Cron 持有这些值的时段和缺少值时的行为。
  • 保持 AppKey、JWT 或二者共存的上游组合，不在 Runtime 重复 Mate 的认证职责。

Considered options

继续让发现与执行携带相同的四项值

优点：内部签名改动少。
缺点：将秘密发送给无需执行授权的 binding 和 metadata operation，违反最小暴露原则。拒绝。

只在 HTTP 实现中忽略发现凭据，保留发现方法参数

优点：调用方兼容性较好。
缺点：类型仍允许未来误用，测试替身也可能继续传播秘密。拒绝。

发现方法移除凭据参数，只有 execute 接收四项值

优点：边界由接口直接表达；Agent、Skill 和 metadata 发现无法获得这些值；execute 逐请求携带 POST Events 收到的非空值。
缺点：需要同步修改内部客户端、发现器和测试替身。接受。

Decision

  • POST /campusclaw-service/v1/sessions/{sessionId}/events 读取精确 Header access-token、X-HW-ID、X-HW-APPKEY 和 Authorization，并只在本次 Agent 执行及其 Child 调用期间由内存对象持有。
  • MateToolClient#listAgentTools 和 #listSkillTools 移除凭据参数；Agent binding、Skill binding、tool metadata 请求只发送普通 JSON Header。
  • 只有 POST /mate-service/v1/runtime/tools/{toolId}/execute 携带收到的非空值。Header 名固定为小写连字符形式 access-token，不使用旧别名 X-Access-Token。
  • 发送 execute 前必须具有 access-token、X-HW-ID 以及 AppKey/JWT 至少一种。AppKey 与 JWT 同时存在时都发送；条件不满足时不发送请求并返回工具执行失败。
  • POST Events 不因缺少执行凭据而被拒绝；Agent、Skill 和 metadata 发现仍可执行。
  • 这些值不写入数据库、Event、Prompt、模型消息或日志；执行结束后 Runtime 不再主动持有。Child 调用使用父执行持有的值；Cron 没有入站调用方值，因此不能发送 execute。

Intentional differences

接口契约变更：POST Events 比变更前多捕获 access-token。

安全加固：发现链路从“收到就发送”改为完全不能接收执行凭据，秘密只到达 execute operation。

架构保持：不增加 resolver、ThreadLocal、持久化凭据或 Runtime 认证器；真实性与动作授权仍由 Mate 决定。

Consequences

  • 正面：发现请求泄露执行凭据的路径被接口和聚焦 HTTP 测试同时关闭。
  • 正面：四项值只在本次 Agent 执行和 Child 调用期间由内存对象传递，共享客户端保持无状态。
  • 负面：没有 access-token 的旧调用方仍能提交 Events，但在执行 Mate 工具时会得到 unavailable/fail-closed 结果。
  • 后续：若某个发现 operation 将来确实需要独立认证，必须定义专用最小凭据，不能复用工具执行值。

Validation

  • RuntimeRequestContextTest 覆盖读取四项值，以及缺少 access-token 时 POST Events 不被本地拒绝但 execute 条件不满足。
  • HttpMateToolClientTest 覆盖 Agent/Skill/metadata 不携带四项 Header、execute 精确携带收到的值、旧 X-Access-Token 不发送。
  • RuntimeEventRoutesTest 覆盖 POST Events 读取 access-token 并交给当次执行的 Service。
