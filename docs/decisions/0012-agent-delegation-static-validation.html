ADR-0012 · Agent 委派静态校验与授权端口

Status: Superseded · Date: 2026-08-17 · Amended: 2026-08-24 · Replaced by: ADR-0022 · 设计文档: agent-delegation · 上游设计: mainagent-subagent-design.md §2.3/§5.1/§5.2/§5.4 · 前置: ADR-0011

Context

统一父子 Agent 调用设计要求 effectiveChildAgents = bindingAgents ∩ enabledAgents ∩ principalAuthorizedAgents − ancestryAgents，且运行时必须校验直接绑定、用户授权、两层深度硬上限和 ancestry 环，不能依赖 Prompt 防止越权或循环。PR #138 已把 bindingAgents（含 description）与 enabled 持久化到本地快照，但没有任何组件消费这些元数据。本决策确定校验组件的边界、深度不变量的承载位置，以及尚无租户身份时授权语义如何落地。

Options considered

  • 校验逻辑分散在 invoke_agent 工具与 Dispatcher 内部
    Pro：组件少一步。
    Con：工具注册（候选发现）与执行前二次校验需要同一套规则，分散必然漂移；无法独立单测规则矩阵。Rejected。
  • Resolver 顺带加载完整子运行时（AgentRuntimeManager.prepare）做校验
    Pro：元数据最全。
    Con：候选发现要为每个绑定物化整个子 Agent（skill 树、prompt），冷启动放大为 N 次远程调用；设计 §5.1 要求轻量摘要。Rejected。
  • 纯函数 Resolver + 元数据/授权双端口 + 类型级深度不变量
    Pro：规则集中一处、可全量单测；加载策略（本地 agentId.json 轻读或完整 prepare）由端口实现方决定；深度与 ancestry 不变量编码进 DelegationContext 构造器，非法状态不可表示。
    Con：多两个端口接口，需在后续 PR 接线。Chosen。

选择理由：静态规则是安全边界，必须可独立穷举验证；执行与加载策略会随后续 PR 演进，不应与规则耦合。

Decision

  • AgentBindingResolver 是无状态纯组件：resolve(parent, principal, invocationChain) 产出候选摘要（供 invoke_agent 工具描述），validate(parent, principal, chain, parentDepth, targetAgentId) 在执行前返回 sealed 裁决（八种拒绝原因枚举）。
  • 候选只来自父快照 bindingAgents；目标不在直接绑定内一律 NOT_DIRECTLY_BOUND，即使该 Agent 存在且用户有权。
  • DelegationContext（§5.4 全 13 字段）的 canonical constructor 强制：1 ≤ delegationDepth ≤ 2、ancestry.size == depth、ancestry.last == parentAgentId、target ∉ ancestry（连带排除自绑定）；delegateTo 在深度 2 抛 IllegalStateException——硬上限由类型保证，元数据与 Skill 配置都无法提高。
  • 子元数据经 ChildAgentMetadataSource 端口获取（agentId → Optional<{version, enabled}>）；返回空即 UNKNOWN_CHILD，fail closed。
  • 版本钉：绑定声明版本时子元数据必须相等，子版本未知视为不兼容；绑定版本留空表示不钉。候选摘要展示子 Agent 实际版本而非父绑定钉值。
  • 授权经 AgentAuthorizationPolicy 端口（AgentPrincipal 含 tenant/user，本地 CLI 为 null）；当前唯一实现 PERMIT_ALL，直接绑定仍是唯一安全边界，租户身份贯通后替换实现而不改调用方。
  • 边缘生命周期标识（session/run/subTask/idempotencyKey/deadline）暂允许 null，由 Dispatcher 与 SubTask 生命周期 PR 填充。

Consequences

  • 正面：规则矩阵（两层链、禁用、自绑定、环、深度、未绑定、版本、授权）全部单测锁定；后续 invoke_agent/Dispatcher 只消费裁决，不再各自实现规则；深度违规在构造期即暴露。
  • 负面：多两个待接线端口；PERMIT_ALL 在多租户上线前不提供真实授权——依赖直接绑定兜底，需在接入租户体系时补 ADR 说明替换时机。
  • 后续：下一 PR 实现 invoke_agent 工具注册（resolve 驱动描述、无候选或深度已满不注册）与执行前 validate 调用；再下一 PR 接入 Dispatcher/TransientRunner 与 SubTask 生命周期，填充边缘标识。
