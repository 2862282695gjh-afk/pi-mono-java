三剑客：AgentSession / Agent / AgentLoop

一轮对话中三者的协作机制与职责边界
项目：CampusClaw（原 pi-mono-java）· 模块：agent-core + coding-agent-cli · 分析日期：2026-07-08

这三个类名相似、职责却截然不同，是一轮对话里分工最核心的三层。一句话区分：

🪟 AgentSession = 会话外壳（转发，不干活）　·　🧠 Agent = 生命周期 + 状态宿主 + 事件总线　·　🔄 AgentLoop = 单轮执行的算法核心（LLM↔工具循环）

另有两位"隐形关键角色"贯穿其中：AgentContext（Loop 与 State 的桥梁）与 AgentState（唯一的状态真相源）。本文一并讲清。

关键观察：Agent 把自己的 AgentState 包进 AgentContext 交给 Loop——三者是通过「共享同一个 state 实例」+「emit 事件回调」两条线协作的，而非直接持有对方引用。Loop 是无状态算法，每次执行新建；Agent 是有状态宿主，跨轮常驻。

🪟 coding-agent-cli 层　AgentSession —— 会话外壳

定位：CLI 会话层的一个"门面 / 转发壳"。持有 Agent 引用 + 若干会话级附带状态（skill registry、sub-agent registry、初始化标志），但不参与一轮对话的执行逻辑。

在一轮中的作用：被 InteractiveMode 当作"拿 agent、读历史、注入插话"的统一入口。它的所有"读写消息"方法全部转发给 agent / state，自身对消息历史零所有权。

modules/coding-agent-cli/.../session/AgentSession.java
AgentSession.java · getHistory / getAgent 都是转发
// 不持有 history 字段 —— 每次现读 agent 的 state public List<Message> getHistory() { return agent.getState().getMessages(); // ← 纯转发 } public Agent getAgent() { return agent; }
为什么需要这一层？InteractiveMode 完全可以直接调 agent。Session 的价值在于封装会话级关注点（持久化、技能注册、子 agent 注册），让 InteractiveMode 不直接耦合 agent-core 内核。但在"一轮对话的执行"这件事上，它是个透明的传声筒。

🧠 agent-core 层　Agent —— 生命周期 + 状态宿主 + 事件总线

定位：agent-core 的门面类，是整个会话唯一长生命周期的对象（一个会话一个 Agent）。它自己不驱动 LLM，把驱动职责完全委托给 AgentLoop。

三个核心职责：

① 状态宿主——持有唯一的 AgentState（消息、model、tools、streaming 标志、错误）。
② 生命周期管理——startExecution 防重入、建取消令牌、新建 context + loop、在虚拟线程异步跑、收尾清理。
③ 事件总线——Loop 产生事件 → emit → 投影回 state + 广播给所有 listeners（UI、持久化）。

① 生命周期入口：startExecution

modules/agent-core/.../agent/Agent.java · 218-269
Agent.java · 每轮新建 context + loop，虚拟线程异步跑
private CompletableFuture<Void> startExecution(List<Message> messages, boolean continueOnly) { synchronized (executionLock) { if (!currentExecution.isDone()) // 防重入 return CompletableFuture.failedFuture(..."Agent is already running"); var signal = new CancellationToken(); // 支持 abort var context = new AgentContext(state); // ✦ 包住自己的 state var loop = new AgentLoop(new AgentLoopConfig(...)); // ✦ 每轮新建 var execution = CompletableFuture.runAsync( () -> { if (continueOnly) loop.continueLoop(context, this::emit, signal); else loop.run(messages, context, this::emit, signal); }, VIRTUAL_THREAD_EXECUTOR) // ✦ 虚拟线程，异步 .whenComplete((u, t) -> { state.setStreaming(false); ... }); currentExecution = execution; return execution; // 立即返回，不阻塞 } }
精妙之处：AgentLoop 是每次执行都 new 一个的无状态对象，而 Agent + AgentState 跨轮常驻。这让"算法"和"宿主"彻底解耦——同一个 Agent 可以连续 prompt 多次，状态自然延续，而 Loop 用完即弃。

② + ③ 事件回流：emit 与 applyEventToState

modules/agent-core/.../agent/Agent.java · 275-322
Agent.java · Loop 的每个事件都经此回流
private void emit(AgentEvent event) { applyEventToState(event); // ① 投影回 state for (var listener : listeners) // ② 广播给 UI/持久化 listener.onEvent(event); } private void applyEventToState(AgentEvent event) { switch (event) { case MessageUpdateEvent e -> { state.setStreaming(true); state.setStreamMessage(e.message()); } // 流式实时投影 case MessageEndEvent e -> { state.setStreaming(false); state.setStreamMessage(null); } case ToolExecutionStartEvent e -> state.addPendingToolCall(e.toolCallId()); case AgentEndEvent e -> state.replaceMessages(e.messages()); // ✦ 最终整体定稿 ... } }
双通道：Loop 边流式产出 → emit 实时把 streamMessage 写进 state（UI 看到字一个个冒出）；轮次结束的 AgentEndEvent 再 replaceMessages 把完整最终历史整体写回。流式与定稿是两条不同的写路径。

🔄 agent-core 层　AgentLoop —— 单轮执行的算法核心

定位：无状态的"LLM ↔ 工具"循环驱动器。由 Agent 在每次执行时新建，跑完即弃。它只认 AgentContext（拿消息、写消息、取工具），不直接碰 Agent 或 AgentState。

在一轮中的作用：在虚拟线程里跑 while 循环，每个 turn = 一次 invokeModel（流式调 LLM）+ 可能的 runToolPhase（执行工具）。循环到"无工具调用且无 follow-up"为止。

Loop 与外界只有两个接口：① 经 AgentContext 读写消息（间接改 state）；② 经 this::emit 回调上报事件。它对 Agent、对 UI、对持久化一无所知——这是它能做成无状态、可复用、可测试的关键。

🌉 隐形主角　AgentContext 与 AgentState

这两个不在标题里，却是一切协作的"底座"。理解它们，才算真正理解三剑客为什么这么分。

AgentContext —— Loop 与 State 的可变桥梁

Loop 拿着它，像一根"操作杆"。它的每个方法都原样转发给持有的 AgentState：

modules/agent-core/.../tool/AgentContext.java · 75-91
AgentContext.java · 全部转发给共享的 state
public List<Message> messages() { return state.getMessages(); } public void appendMessage(Message m) { state.appendMessage(m); } // ← 转发 public void appendMessages(List<?> ms) { ms.forEach(state::appendMessage); } public void replaceMessages(List<Message> m){ state.replaceMessages(m); }
为什么要有这一层？Agent 把自己的 state 包进 context 交给 Loop。Loop 写 context ⇔ 写 state ⇔ Agent 的 emit 也能立刻读到。Context 让 Loop不必持有 Agent 引用就能改状态，把"循环算法"和"宿主对象"的耦合降到只剩"共享 state + 事件回调"。

AgentState —— 唯一的状态真相源

整个体系里唯一真正存 List<Message> 的地方。读写锁保护，所有读写都 copyOf 防御性拷贝。

AgentState 底层 · 唯一真相源
AgentContext（包住 state，转发） 桥梁
AgentLoop（经 context 读写） · Agent（经 emit 投影） 双写者
AgentSession.getHistory()（只读转发） 外壳

💡 三个关键设计洞察

① 「算法即弃、宿主常驻」的分层。AgentLoop 每次 prompt 都 new 一个、跑完丢弃；Agent 和 AgentState 贯穿整个会话。这让循环逻辑可以做得纯粹（无状态、易测、可复用），而跨轮的状态连续性由 Agent 兜底。
② 双线解耦：共享 state + 事件回调。Agent 和 Loop 之间没有直接的持有引用——数据线是「共享同一个 AgentState 实例」（Loop 经 context 写，Agent 经 emit 读/写），控制线是「this::emit 回调」。Loop 不知 Agent 存在，Agent 也不直接操控 Loop 内部，两者只通过这两条线跳探戈。
③ 流式与定稿是两条写路径。Loop 边产出边 emit(MessageUpdate) → state.streamMessage（临时、UI 逐字渲染）；轮次结束才 emit(AgentEndEvent) → state.replaceMessages（整体、最终定稿）。这解释了为什么 UI 能实时滚动、而历史记录是"完整一轮"的单位。

🪜 一句话串起来：

InteractiveMode 经 AgentSession（转发壳）调 Agent（建 context + 新 Loop，虚拟线程异步跑）；AgentLoop（无状态算法）经 AgentContext 改 AgentState（唯一真相源）、经 emit 把事件回流给 Agent（投影回 state + 广播 UI）；循环结束 AgentEndEvent 定稿，.join() 解除阻塞，一轮对话完成。
