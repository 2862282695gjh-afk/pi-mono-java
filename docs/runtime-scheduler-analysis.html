总览 调度器是什么

CampusClaw（原 pi-mono-java）的 runtime 调度器是驱动 Coding Agent 运转的核心引擎：决定何时调用 LLM、何时执行工具、何时注入用户中途打断的消息、何时停止。核心是 AgentLoop.runInternal()——一个单层 while(!signal.isCancelled()) 循环 + continue 分支。

它分三层：AgentLoop（纯调度）→ Agent（有状态门面，跑在虚拟线程上）→ AgentSession（应用层 prompt 展开 + 路由）。整套建立在 Reactor 流式响应与 sealed AgentEvent 事件模型之上。

与 TS 版的关键差异：作者把 TypeScript 版（pi-mono）的双层嵌套循环（外层跑 follow-up、内层跑 tool+steering）重构为 Java 版的单循环 + continue——工具阶段返回 steering 消息作为下一轮 pending 输入并 continue，无工具分支再查 follow-up。控制流更扁平，并发模型从 async/await 换成虚拟线程，事件从 union 类型换成 sealed interface + Jackson 序列化。

Layer 1 AgentLoop · 单循环调度

com.campusclaw.agent.loop.AgentLoop（405 行）是纯调度器——不持有应用状态，构造时把 AgentLoopConfig（一个 12 字段 record）的字段拆成 final 依赖。两个入口最终都汇入 runInternal()：

  • run(prompts, context, listener, signal) —— 用新 prompt 启动
  • continueLoop(context, listener, signal) —— 从已有上下文继续（重试/恢复）

listener 是 AgentEventListener（函数式接口，onEvent(AgentEvent)），所有状态变化通过它向外广播。

单循环的精髓：没有内外两层 while。工具分支把 steering 消息作为返回值交给 pendingTurnInputs 再 continue——下一轮顶部重新 emitPendingInputs 把它们注入上下文（不跳过当前工具结果）。无工具分支才查 follow-up，有则设 pending 继续，无则 break。整段循环体保持在一个方法内、圈复杂度可控。

private List<Message> runInternal(
        List<Message> prompts, AgentContext context,
        AgentEventListener listener, CancellationToken signal) {
    AgentEventListener eventListener = listener != null ? listener : event -> {};
    if (!prompts.isEmpty()) {
        context.appendMessages(prompts);
    }
    List<Message> pendingTurnInputs = List.copyOf(prompts);
    eventListener.onEvent(new AgentStartEvent());
    int turn = 0;
    try {
        while (!signal.isCancelled()) {
            turn++;
            AcpTransport.note("AgentLoop.turn=" + turn + " start msgCount=" + context.messages().size());
            eventListener.onEvent(new TurnStartEvent());
            emitPendingInputs(pendingTurnInputs, eventListener);

            // 流式调用 LLM（transform→convert→Flux 消费）
            AssistantMessage assistantMessage = invokeModelTraced(turn, context, eventListener, signal);
            context.appendMessage(assistantMessage);
            context.setAssistantMessage(assistantMessage);
            eventListener.onEvent(new MessageEndEvent(assistantMessage));

            if (assistantMessage.stopReason() == StopReason.ERROR
                    || assistantMessage.stopReason() == StopReason.ABORTED) {
                eventListener.onEvent(new TurnEndEvent(assistantMessage, List.of()));
                break;
            }

            var toolCalls = extractToolCalls(assistantMessage);
            if (!toolCalls.isEmpty()) {
                // 执行工具 + drain steering；steering 作为下一轮 pending
                pendingTurnInputs = runToolPhaseTraced(turn, context, signal, eventListener, assistantMessage, toolCalls);
                continue;
            }

            // 无工具 → 查 follow-up 决定是否续跑
            var followUpMessages = drainFollowUpMessages();
            eventListener.onEvent(new TurnEndEvent(assistantMessage, List.of()));
            if (followUpMessages.isEmpty()) {
                break;
            }
            context.appendMessages(followUpMessages);
            pendingTurnInputs = followUpMessages;
        }
        return context.messages();
    } finally {
        eventListener.onEvent(new AgentEndEvent(context.messages()));
    }
}

流式 invokeModel · Reactor + 取消

invokeModel() 是 LLM 边界：先 transformContext（异步剪枝/注入），再 convertToLlm（转 LLM 形态消息），然后 streamFunction.stream(...) 拿到 Reactor Flux。取消靠 CancellationToken 注册回调，向一个 Sinks.One<Object> 发空信号，用 takeUntilOther(cancelSink) 撕掉流。

java
private StreamConsumeResult consumeStream(AssistantMessageEventStream stream,
        Sinks.One<Object> cancelSink, AgentEventListener listener, CancellationToken signal) {
    AssistantMessage assistantMessage = null;
    var assistantStarted = false;
    for (var event : stream.asFlux().takeUntilOther(cancelSink.asMono()).toIterable()) {
        if (signal.isCancelled()) {
            break;   // 到达后立即停，不再 block
        }
        var currentMessage = extractAssistantMessage(event);
        if (!assistantStarted) {
            listener.onEvent(new MessageStartEvent(currentMessage));
            assistantStarted = true;
        }
        if (!(event instanceof AssistantMessageEvent.StartEvent)) {
            listener.onEvent(new MessageUpdateEvent(currentMessage, event));
        }
        assistantMessage = currentMessage;
    }
    return new StreamConsumeResult(assistantMessage, assistantStarted);
}

// 取消后合成 ABORTED 消息，让外层循环干净退出（避免 result().block() 在已拆除的流上挂死）
private AssistantMessage synthesizeAbortedMessage(StreamConsumeResult result, ...) {
    return new AssistantMessage(... , StopReason.ABORTED, null, System.currentTimeMillis());
}
取消契约：Reactor 的 takeUntilOther(cancelSink.asMono()) 让取消信号能穿透正在进行的流。取消后不调 stream.result().block()（那会在已拆除的流上永久挂起），而是合成一个 StopReason.ABORTED 的 AssistantMessage——上层看到 ABORTED 就 break 退出循环。这是注释里点名的 bug 规避。

private List<ToolResultMessage> executeInParallel(
        List<ToolCallWithTool> calls, AgentContext context, CancellationToken signal, AgentEventListener listener) {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        var futures = new ArrayList<Future<ToolResultMessage>>(calls.size());
        for (var call : calls) {
            futures.add(executor.submit(() ->
                execute(call.tool(), call.toolCall(), call.validatedArgs(), context, signal, listener)));
        }
        var results = new ArrayList<ToolResultMessage>(calls.size());
        for (var future : futures) {
            results.add(future.get());   // 按提交顺序取 → 结果保源顺序
        }
        return List.copyOf(results);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("Interrupted while executing tools in parallel", e);
    }
}
虚拟线程 per task：每个工具一个虚拟线程——对 IO 密集的工具（bash、网络请求）几乎零开销、可大量并发。结果仍按提交顺序 future.get() 收集，保证 ToolResultMessage 顺序确定、可重放（与 TS 版的「按源顺序 emit」对齐）。

双投递通道：steering/follow-up 各有两种来源——MessageQueue（线程安全队列）和可选的 SteeringMessageSupplier（函数式回调）。drainSteeringMessages() 优先用 supplier，为空再退回 queue.drain()。这让调度器既能接「往队列塞消息」的简单用法，也能接「按需拉取」的自定义逻辑。

Layer 2 Agent · 虚拟线程门面

com.campusclaw.agent.Agent（373 行）是无状态 AgentLoop 的有状态外壳。核心 startExecution() 做四件事：① executionLock 串行化（运行中再调直接失败）；② 构造 AgentLoop；③ 提交到 VIRTUAL_THREAD_EXECUTOR；④ whenComplete 清理状态。

private CompletableFuture<Void> startExecution(List<Message> messages, boolean continueOnly) {
    synchronized (executionLock) {
        if (!currentExecution.isDone()) {
            return CompletableFuture.failedFuture(
                new IllegalStateException("Agent is already running"));
        }
        var signal = new CancellationToken();
        currentSignal = signal;
        var context = new AgentContext(state);
        var loop = new AgentLoop(new AgentLoopConfig(piAiService, model, ...));

        var execution = CompletableFuture.runAsync(() -> {
            if (continueOnly) loop.continueLoop(context, this::emit, signal);
            else             loop.run(messages, context, this::emit, signal);
        }, VIRTUAL_THREAD_EXECUTOR).whenComplete((unused, throwable) -> {
            state.setStreaming(false);
            state.setStreamMessage(null);
            state.clearPendingToolCalls();
            synchronized (executionLock) { currentSignal = null; }
            if (throwable != null) state.setError(formatError(throwable));
        });

        currentExecution = execution;
        return execution;
    }
}

private void emit(AgentEvent event) {
    applyEventToState(event);                  // 事件 → AgentState
    for (var listener : listeners) {   // CopyOnWriteArrayList 广播
        try {
            listener.onEvent(event);
        } catch (RuntimeException e) {
            // 监听器不应打断 agent 运行；把 bug 暴露到日志
            log.warn("agent event listener threw exception (event={})",
                     event.getClass().getSimpleName(), e);
        }
    }
}
容错纪律：emit() 对每个监听器单独 try/catch——一个有 bug 的监听器抛异常只进 SLF4J log.warn，不会拖垮整次 agent 运行。这正是 CLAUDE.md 「禁止静默 catch」规则的正确实践：异常被真实记录、带上下文（event 类型），而非吞掉。

并发 MessageQueue · 线程安全

steering/follow-up 队列是 com.campusclaw.agent.queue.MessageQueue——ReentrantLock 守护 ArrayDeque<Message>，支持两种 DeliveryMode。因为 steer()/followUp() 可能从任意线程调用（UI 线程、WebSocket 线程），而 drain 发生在虚拟线程的循环里，跨线程安全是硬需求。

DeliveryModedrain 行为对应场景
ALL（默认）取出全部并清空队列一次性消化所有积压
ONE_AT_A_TIME只取队首一条，其余留到下轮逐条确认式交互（每轮只见一条打断）

java
private List<Message> drainLocked(DeliveryMode mode) {
    if (messages.isEmpty()) {
        return List.of();
    }
    return switch (mode) {
        case ALL -> {
            var drained = new ArrayList<Message>(messages);
            messages.clear();
            yield List.copyOf(drained);
        }
        case ONE_AT_A_TIME -> List.of(messages.removeFirst());
    };
}
